# Решение

## Изменения

- Добавлена миграция `002_order_discounts.sql`: nullable-поле `amount_paid_kop`.
- Нормализация, модель и репозиторий сохраняют `amountPaid` в копейках.
  Одинаковая обработка используется для синхронизации и вебхуков.
- Дневная статистика возвращает `total`, `gross`, `discount`, `net`.
  `total = gross`, `discount = gross - net`. Учитываются только `paid`,
  дни без оплат возвращаются с нулевыми суммами.
- Смещение таймзоны определяется на момент создания каждого заказа.
- Перевод рублей в копейки выполняется через десятичную запись и BigInt,
  чтобы не терять копейку из-за двоичной арифметики. Доли копейки отбрасываются;
  суммы вне безопасного диапазона целых чисел Number отклоняются.
- Для совпадающей версии заказа разрешено заполнение неизвестной оплаты:
  отдельный условный UPDATE меняет только NULL, если совпадают updatedAt
  и остальные сохранённые поля. Более старые версии по-прежнему игнорируются.
- Сигнатура `createContainer(db, api)` и интерфейс `OrdersApi` сохранены.

## Причина жалобы и расследование

Внешний API возвращает для `c_7` таймзону `Europe/Berlin`.
Раньше сервис вычислял смещение через `new Date()` и применял его к любому
историческому заказу. В момент проверки это было UTC+1. С 29 марта 2026 года
Берлин использует UTC+2, поэтому часть вечерних UTC-заказов попадала
в предыдущий календарный день.

Пример из БД: `o_02357`, сумма 9306 рублей, `createdAt=2026-03-29T22:40:08Z`.
В Берлине это 30 марта, 00:40:08. Старый расчёт относил заказ к 29 марта.
Аналогично `o_02448` на 1823 рубля переместился с 30 на 31 марта,
а `o_02545` и `o_02547` относятся уже к 1 апреля и исключаются из периода.

Для проверки прочитаны оплаченные заказы из БД и независимо сгруппированы
через `Intl.DateTimeFormat` с `timeZone: 'Europe/Berlin'`.
Получены gross: 24736, 58233, 38333, 59684, 35401 рублей за 27–31 марта.
Они совпадают с исправленным HTTP-ответом. Отдельного отчёта платёжной
системы в материалах нет; сверка выполнена с исходными заказами.

## Допущения и особенности API

- Источник фактической оплаты — `amountPaid`. Процент не используется
  для повторного вычисления уже переданной оплаты.
- При отсутствии `amountPaid` в БД сохраняется NULL, а статистика считает
  заказ без скидки (`net = gross`). Это правило применяется и к гипотетическому
  заказу только с `discountPercent`; оно требует согласования для реального API.
- Нулевая оплата сохраняется как 0 и не заменяется исходной суммой.
- Рубли принимаются числами и строками. День определяется по `createdAt`,
  как в исходном сервисе; дата оплаты отдельно не предоставляется.
- Поля скидок отсутствуют в старых записях API. При полном чтении получено
  5030 записей на 52 страницах, у 3853 присутствовали оба скидочных поля.
  В просмотренной последовательности они появились с заказов от 15 марта.
  Количество полученных записей не обязательно равно числу уникальных заказов.
- Клиент уже учитывает ограничения частоты, 429 и ошибки внутри HTTP 200.
  Синхронизация обрабатывает завершение пустой страницей с прежним курсором.

## Проверки

Использовались Codex для анализа, диагностики и предложений кода,
WebStorm для редактирования и запуска, Postman для HTTP-запросов,
Navicat для просмотра БД. Изменения выполнялись пошагово совместно с ассистентом.

Проверка типов: `npm run typecheck`.
Полный набор: `TEST_DATABASE_URL=postgres://postgres:postgres@127.0.0.1:55432/orders_test npm test`.
После последних изменений пользователь подтвердил успешное прохождение проверок.

Добавлены проверки перехода времени в Берлине и независимости исторических
итогов от зимней/летней даты запуска; денежных значений 0.29, 1.15 и 10.999;
скидок через вебхуки, полной скидки, строковых сумм и оплаты при синхронизации.
Ожидания существующих тестов статистики дополнены новыми полями.

Для итогового сценария подготовлена отдельная чистая база `orders_result`,
затем выполняются миграции, полный POST /sync, доставка вебхуков и GET
статистики. Ответ сохранён в `result.json`. Локальный PostgreSQL запущен
отдельным контейнером на порту 55432 из-за конфликта стандартного порта;
mock API запускается через Docker Compose на 4000. Сервис слушает 3000.

## Что осталось

- Атомарно применять проверку версии при обычном upsert: сейчас между
  чтением и записью возможна гонка конкурентных синка и вебхука.
- Добавить отдельные тесты обогащения NULL при равном updatedAt и миграции
  базы с существующими записями.
- Уточнить контракт для противоречивых сумм, отсутствующей оплаты при
  наличии процента, избыточной точности и допустимых денежных диапазонов.
- Обработать безопасный диапазон не только отдельного заказа, но и суммы дня;
  ужесточить разбор строковых сумм (например, пустой строки).
- Продумать обогащение старых записей, если API уже возвращает более старую
  версию, чем сохранённая из вебхука. Итоговый сценарий на чистой БД
  не требует такого восстановления.
