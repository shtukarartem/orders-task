# Инструкции для агентов разработки

## Задача и исходные документы

Работайте в `orders-aggregator/`. Сначала прочитайте `TASK.md` и `README.md`.
В случае расхождений требования `TASK.md` имеют приоритет над этим планом.
Ориентир задания — до 3 часов. Не тратьте основное время на рефакторинг вне задачи.

Нужно:

1. Добавить учёт скидок в `GET /customers/:id/daily-totals`.
2. Найти и исправить причину расхождения статистики клиента `c_7` за
   `2026-03-27`–`2026-03-31` с отчётом платёжной системы.
3. Добавить тесты и получить реальные артефакты сдачи: `result.json` и `SOLUTION.md`.

Формат элемента ответа:

```json
{"date":"2026-02-10","total":2500,"gross":2500,"discount":412.5,"net":2087.5}
```

- `gross` — сумма оплаченных заказов до скидок.
- `net` — фактически оплаченная сумма.
- `discount = gross - net`.
- `total = gross`, поле сохраняется для обратной совместимости.
- Суммы в ответе — рубли с точностью до копейки, внутри — целые копейки.
- Учитываются только заказы со статусом `paid`.
- Сохраняйте группировку по `createdAt`, календарным дням таймзоны клиента,
  включительность обеих дат периода и дни без оплат с нулевыми суммами.

## Ограничения

- Не меняйте сигнатуру `createContainer(db, api)` и интерфейс `OrdersApi`.
- Сохраняйте поведение повторных и устаревших вебхуков.
- Изменения схемы оформляйте новой миграцией; не переписывайте `001_init.sql`.
- Предусмотрите существующие записи в БД и старые заказы без новых полей.
- Не подменяйте реальные результаты фейковыми данными и не редактируйте образ
  внешнего API ради прохождения сценария.
- Не удаляйте существующие проверки ради зелёных тестов. Точные ожидания JSON
  в тестах статистики потребуется дополнить новыми полями, сохранив смысл проверок.
- Не уничтожайте чужие данные или контейнеры при подготовке чистой БД.

## Устройство проекта

Стек: Node.js 20+, TypeScript, Fastify, PostgreSQL 16, Zod, Vitest.

| Файлы | Назначение |
| --- | --- |
| `src/clients/orders-api.ts` | HTTP-клиент внешнего API, ограничения частоты и повторы |
| `src/services/orders.ts` | Валидация и нормализация заказа, применение обновлений |
| `src/repositories/orders.ts` | Модель заказа, чтение и запись в БД |
| `src/services/sync.ts` | Обход страниц и статистика синхронизации |
| `src/services/totals.ts` | Агрегация по дням |
| `src/services/customers.ts` | Получение и кеширование таймзоны клиента |
| `src/utils/money.ts`, `src/utils/time.ts` | Денежные преобразования и даты |
| `src/routes/` | HTTP-маршруты |
| `migrations/` | SQL-миграции |
| `test/` | Unit-тесты и интеграционные тесты с настоящим PostgreSQL |

В тестах внешний API заменён `FakeApi` из `test/helpers.ts`.
Интеграционные тесты очищают таблицы: используйте отдельную БД `orders_test`.

## Что уже изучено

На момент подготовки этого файла код не менялся, сервис и тесты не запускались.
Прочитаны исходники, миграция, документация и существующие тесты.
Следующие наблюдения — отправные точки для расследования.

### 1. Новые поля теряются

В `src/services/orders.ts` схема Zod не содержит `discountPercent` и `amountPaid`.
В модели и БД хранится только `amountKop`. Скидки нужно провести через весь путь:
приём → нормализация → сохранение → чтение → агрегация → ответ.
Путь приёма общий для синка и вебхуков.

### 2. Неверное смещение таймзоны

В `TotalsService.daily()` смещение вычисляется через
`tzOffsetMinutes(timezone, new Date())` и применяется ко всем заказам.
Для зон с сезонным переводом времени это даёт неправильные календарные дни.
Нужно определять локальную дату каждого заказа по IANA-таймзоне на момент
его `createdAt`, а не по текущей дате или началу периода.

Это вероятная причина жалобы за конец марта, но таймзона `c_7` и конкретные
проблемные заказы ещё не проверены. Не описывайте гипотезу как подтверждённый
результат до проверки данных внешнего API.

### 3. Подтверждена потеря копейки при преобразовании денег

`toKop()` использует `Math.floor(rub * 100)`. Отдельная проверка в Node.js показала:

```text
0.29 * 100 = 28.999999999999996 → 28 копеек
1.15 * 100 = 114.99999999999999 → 114 копеек
```

Исправьте преобразование с учётом десятичного представления и безопасного
целочисленного диапазона. Существующий тест требует `10.999 → 1099`:
нельзя просто заменить `floor` на округление до ближайшей копейки.
Проверьте числовые и строковые входы, включая фактические форматы внешнего API.

### 4. Возможна гонка обновлений

`OrdersService.apply()` сначала читает версию заказа, затем отдельно выполняет
безусловный upsert. При конкурентном синке и вебхуке старая версия может
перезаписать новую. Если исправляете, проверку `updatedAt` выполняйте атомарно
в БД и сохраняйте корректный результат `created` / `updated` / `stale`.
Это дополнительное замечание; не позволяйте ему вытеснить обязательные результаты.

## Порядок выполнения

### Этап 1. Запуск и подтверждение исходного состояния — около 25 минут

1. Проверьте архитектуру через `uname -m`, загрузите соответствующий образ из
   родительской папки по инструкции README.
2. Поднимите сервисы Docker Compose, установите зависимости через `npm ci`,
   примените миграции.
3. Запустите `npm test` и `npm run typecheck`; зафиксируйте исходные ошибки,
   если они есть.
4. Изучите реальные ответы внешнего API: таймзону `c_7`, представление денег,
   наличие скидочных полей, поведение страниц и обновлений.
5. Воспроизведите расхождения на границах локальных суток.

### Этап 2. Деньги и скидки — около 40 минут

1. Определите и запишите правила для отсутствующих и некорректных полей.
2. Используйте `amountPaid` как источник фактической оплаты, когда оно передано.
   Не пересчитывайте его из процента без основания: правила округления внешней
   системы могут отличаться.
3. Решите, что делать при отсутствии `amountPaid`, наличии только процента и
   противоречии между полями. Обоснуйте решение реальными данными и совместимостью;
   не превращайте это предложение в неподтверждённое требование.
4. Добавьте миграцию и расширьте нормализацию, модель и репозиторий.
5. Исправьте денежное преобразование и покройте пограничные случаи тестами.
6. Учтите обновление существующих записей: равный `updatedAt` сейчас считается
   устаревшей версией, поэтому повторный синк сам по себе не обогатит старые строки
   новыми полями. Выберите явную стратегию и опишите её ограничения.

### Этап 3. Статистика и таймзоны — около 30 минут

1. Исправьте определение локального календарного дня заказа.
2. Сохраните корректную выборку заказов около обеих границ периода.
3. Суммируйте `gross` и `net` в копейках, вычисляйте разницу в копейках,
   переводите в рубли только при формировании ответа.
4. Для каждого дня возвращайте все пять полей, включая нулевые дни.

### Этап 4. Надёжность обновлений — около 15 минут

При наличии времени устраните гонку версий атомарной записью и добавьте
регрессионный тест с конкурентными обновлениями. Иначе явно укажите проблему
в `SOLUTION.md` как оставшееся ограничение.

### Этап 5. Проверки — около 35 минут

Проверяйте изменения по мере реализации. Перед финальным сценарием выполните
полный `npm test` и `npm run typecheck`.

Минимальные случаи:

- заказ без скидки, частичная и полная скидка;
- несколько заказов в одном дне, `total = gross`, `discount = gross - net`;
- суммы `0.29`, `1.15`, строки с копейками и отбрасывание долей копейки;
- выбранная совместимость с отсутствующими новыми полями;
- невалидные значения по принятым правилам;
- одинаковая обработка через синк и вебхуки;
- повторное и устаревшее событие, изменение суммы и статуса свежим событием;
- исключение `pending` и `refunded`, изоляция клиентов, нулевые дни;
- локальная полночь до и после смены смещения в таймзоне клиента;
- независимость исторической статистики от текущей даты запуска;
- границы запрошенного периода;
- миграция на существующей схеме с записями, а не только на пустой БД.

### Этап 6. Финальный сценарий и сдача — около 35 минут

Сформируйте результат строго в порядке из `TASK.md`:

1. Подготовьте чистую БД проекта и выполните `docker compose up -d`.
2. Запустите сервис с актуальными миграциями.
3. Выполните `POST /sync` и дождитесь успешного завершения.
4. Выполните отправку вебхуков и дождитесь её завершения:

   ```bash
   docker compose run --rm orders-api webhooks --target http://host.docker.internal:3000/webhooks/order
   ```

5. Получите и сохраните ответ:

   ```bash
   curl --fail-with-body --silent --show-error \
     'http://localhost:3000/customers/c_7/daily-totals?from=2026-03-27&to=2026-03-31' \
     --output result.json
   ```

6. Проверьте, что файл содержит успешный ответ: пять дат по порядку,
   требуемые поля и согласованные суммы. Независимо сверьте расчёт с исходными
   заказами и локальными датами, а не только с той же функцией агрегации.
7. Подготовьте `SOLUTION.md`: изменения, подтверждённая причина расхождения,
   способ расследования, проверки и их результаты, особенности внешнего API,
   допущения и оставшиеся улучшения.
8. Обновите README в части формата ответа и необходимых действий для запуска.

`result.json` и `SOLUTION.md` должны лежать в корне `orders-aggregator/`, рядом
с `TASK.md` и `package.json`. В сдаваемый архив не включайте `node_modules`,
образы Docker и локальные секреты.

## Готовность и передача работы

Работа завершена, когда требования реализованы, проверки выполнены, причина
жалобы подтверждена данными, а оба обязательных файла подготовлены.
Без `result.json` задание не принимается.

При передаче другому агенту сообщите: изменённые файлы, принятые решения,
выполненные проверки и ошибки, состояние БД и запущенных процессов,
следующий конкретный шаг. Если окружение помешало проверке, укажите это явно;
не заявляйте о прохождении невыполненных тестов.
